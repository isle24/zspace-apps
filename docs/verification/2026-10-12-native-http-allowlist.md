# 原生 HTTP 白名单缺了 20 条路径（只在 Mac 客户端里坏）

## 这是怎么发现的

接着上一轮的思路（"不能登录验证 ≠ 不能减少风险"），这轮把**前端 ↔ Tauri 的接线**逐个核对。
Tauri 的原生 HTTP 插件有一份**路径白名单**（`src-tauri/capabilities/default.json`），
只有列进去的路径才允许从 webview 发出请求。

于是写了个对比：**应用真正请求的路径**（从 `api/official-nas.ts` 的 operations 表 +
代码里出现的 NAS 路径里提取，去重 56 条）**减去白名单**。

结果：**缺 20 条**。

## 缺的是什么（也就是 Mac 客户端里会坏的功能）

| 缺失路径 | 在客户端里会坏掉的功能 |
| --- | --- |
| `/splay/` | **音乐播放**（音频原流走这个前缀） |
| `/zvideo_static/` | **影视海报封面** |
| `/zmusic_static/` | 音乐封面（这台设备本来也 404，但路径要对） |
| `/system/home` | **控制面板概览** |
| `/system/recent` | **右上角资源挂件的数据** |
| `/system/delay` | 挂件里的延迟项 |
| `/task/list` | **任务中心的设备任务** |
| `/manager/services`、`/manager/v2/processes` | 服务与进程列表 |
| `/zrps/api/speed/query` | **远程访问的上传下载速度** |
| `/downloader/*`（9 条） | **下载中心的全部操作**：添加链接/磁力、协议列表、保存目录、全部开始/暂停 |
| `/transcode/decrypt/thumb` | 加密影片的缩略图 |

**为什么一直没发现**：网页版走的是 `space-proxy` 的**另一套白名单**（我在前几轮为播放
逐一补过 `/play/`、`/splay/`、`/zvideo_static/`…），所以浏览器里一切正常；
而 Mac 客户端……本来就没人在里面点过音乐和影视。这正是"没验证过"的真实代价。

## 修法

把 20 条按现有风格补齐（`http://**:*<path>` 与 `https://**:*<path>` 各一条），
条目数 96 → **136**。补齐后重跑同一个对比：**仍缺 0 ✓**。

## 加了一道护栏

`scripts/static-audit.mjs` 现在会做同样的对比：
从 `official-nas.ts` 提取请求路径，与 capability 里的白名单比对，
**缺任何一条就报错**。

```
=== macOS 打包集成（0）===
```

以后谁加了新接口却忘了同步原生白名单，这里会立刻拦下 —— 而不是等到"用户在某台 Mac 上
发现音乐放不了"。

## 打包验证

重新打包：配置核对通过、`codesign --verify --deep --strict` 通过、应用启动、sidecar 200 ✓
（白名单是编译期嵌进 app 的，所以必须重新打包才生效。）

## 还没验证的

白名单补齐解决的是"**允许发请求**"。至于请求发出后**能不能真的播出来**，
仍然要登录后才知道（这也是我一直在等的那件事）。
但至少现在，"客户端里点音乐会静默失败"这个已知原因已经排除。
