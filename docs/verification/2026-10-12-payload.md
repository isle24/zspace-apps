# 产物与传输：两个"白白多传"的地方

这轮看构建产物本身。发现两处浪费，都不影响功能，但影响加载。

## 1. NAS 的反代不会 gzip —— 每次首屏多传 1.1 MB

实测线上拉 `client.js`：

```
未压缩: 964,958 字节（无 Content-Encoding）
```

`space-proxy` 用的是 `http.FileServer`，没有压缩。而这台 NAS 的 nginx 也不会替它压。

**修法（构建期预压缩 + 按需发送）**

- `deploy/nas-appstore/build.sh`：构建时对 `.js/.css/.html/.svg/.json/.webmanifest`
  生成同名 `.gz`（gzip -9，`mtime=0` 保证可复现）。**压缩 21 个文件，省下 1,202 KB**。
- `deploy/nas-appstore/proxy/main.go`：新增 `precompressedFiles`，
  客户端 `Accept-Encoding: gzip` 且存在 `.gz` 时直接发压缩版本，
  带 `Content-Encoding: gzip` 与 `Vary: Accept-Encoding`（缓存不会串味），
  否则落回普通静态服务。

**实测（线上）**

| 请求 | 传输 |
| --- | --- |
| `client.js`（带 gzip） | **271,737 字节** |
| `client.js`（`Accept-Encoding: identity`） | 964,958 字节（正确降级） |

## 2. 壁纸是 8K —— 单文件 1.1 MB

`wallpaper-fnos.webp` 是 **7680×4320**。任何屏幕都用不到（常见 Retina 全屏 2880×1800）。

缩到 **3200×1800 / 质量 82**：**1,092 KB → 164 KB**（省 85%）。
放大到 1:1 与 8K 原图逐像素对比，平滑渐变看不出差别（对比图见提交说明）。

## 首屏总账（实测，未登录时的登录页）

| 指标 | 之前 | 现在 |
| --- | --- | --- |
| 传输字节 | ≈ 1,602 KB | **440 KB** |
| 解压后字节 | 1,602 KB | 1,602 KB（内容没变） |
| 请求数 | 7 | 7 |
| 控制台异常 | — | **0** |

最大三项：`client.js` 266 KB（原 942）、`store.js` 138 KB（原 465）、两份 CSS 19+16 KB。

## 顺带加的护栏

`build.sh` 结束时会打印体积构成，超过 **6 MB** 就警告 ——
防止以后又悄悄塞进一张 8K 大图或一个用不上的大依赖。

## Mac 客户端

壁纸也在客户端包内，已重新打包（二进制 18.8 MB，含压缩后的壁纸）。
另外客户端从磁盘加载，不依赖上面这套 gzip（那是给网页版用的）。

# 第二轮：按需加载（hls.js）与商店拆包的尝试

## 成果：主包 942 KB → 381 KB

`hls.js` 一直是**静态 import**：942 KB 的主包里约 561 KB 是给"看视频"准备的 ——
只看照片、只放音乐的用户白下载。改成用到才 `import("hls.js")`：

| chunk | 之前 | 现在 |
| --- | --- | --- |
| `client-*.js`（首屏必下） | 942 KB | **381 KB**（gzip 96 KB） |
| `hls-*.js`（点开视频才下） | — | 561 KB（gzip 179 KB） |

代价是"能不能用 hls.js"从同步判断变成异步判断。原先 `hlsHandled` 直接决定要不要写
`src`，异步之后换成三态：

```
pending -> 还没结论，先不写 src（避免浏览器用原生方式去啃 m3u8，报一次解码错误）
hls     -> hls.js 接管，src 留空
native  -> 交给浏览器（Safari 原生 HLS / 本来就不是 HLS 的地址）
```

**没有**自己再写一个"有没有 MediaSource"的同步判断去提前短路 —— 那等于把
`Hls.isSupported()` 抄一份，两边迟早不一致。就让 hls.js 自己回答。

## 首屏总账（本轮结束，实测）

| 阶段 | 传输 |
| --- | --- |
| 本轮开始时 | ≈ 1,602 KB |
| 预压缩 + 壁纸瘦身之后 | 440 KB |
| **hls.js 按需加载之后** | **255 KB** |

控制台异常 0。

## ⚠️ 需要登录后才能确认的一件事

我改动了**视频播放路径**（hls.js 的加载时机）。单测覆盖了选路逻辑
（HLS 交给 hls.js、STRM 跳转不交给它、渐进式地址保留 src），
但**真实播放没验证** —— 页面还停在登录页（上一轮验会话过期造成的）。
登录后第一件事应该是：打开影视中心放一部片子，确认能正常播放。

## 商店拆包：试了四轮，停手，结论记在这里

`fnos-store-*.js`（418 KB / gzip 126 KB）仍在首屏里，因为它**不是**纯商店代码 ——
用 sourcemap 看，它装着商店 + `api/client.ts`、`api/official-nas.ts`、`modules/common.tsx`
等"两个入口共用"的模块。主入口为了拿自己的依赖，不得不把这整块下下来。

四轮尝试与结果：

| 拆法 | 结果 |
| --- | --- |
| 只把商店组件 `manualChunks` | 商店块 264 KB，**仍被首屏引用** |
| \+ node_modules 独立成 vendor | 商店块不变，vendor 却是 1,033 KB，仍被引用 |
| \+ api 层独立成块 | 商店块降到 111 KB，**仍被引用** |
| \+ 其余 UI 模块独立成块 | 仍有残留（`StoreServiceSettings` 等） |

结论：**停手**。继续拆下去收益有限（最多再省 126 KB），
而**未登录状态下我无法验证商店窗口的懒加载路径** —— 万一拆坏，商店就打不开了。
配置已回退到"已验证"的那一版，把这段过程与结论写进了 `vite.config.ts` 的注释，
免得下次又有人从头试一遍。

真要做得彻底，应该反过来：让 `api/` 与共用 UI **不依赖商店**，
商店只依赖它们 —— 那属于结构调整，等商店接入完成、能整体验证时再动。
