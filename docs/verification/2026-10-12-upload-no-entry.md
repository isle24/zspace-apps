# 上传：整条链路都实现了，但界面上没有入口

## 查到了什么

延续"只在客户端坏 / 没人点过"的排查思路，这轮看**原生文件对话框与落盘**。
先找上传的入口在哪 —— 结果：

| 层 | 状态 |
| --- | --- |
| SDK（分片哈希、断点、临时文件、错误码） | ✅ 完整实现（`official-upload.ts`、`upload-hashes.ts`、`upload-sources.ts`） |
| 原生侧（文件选择、读字节、Rust 哈希 worker） | ✅ 完整实现（`upload_source.rs`、`upload_hash.rs`） |
| 原生白名单 | ✅ 已包含 `/v2/file/upload`、`/v2/file/tmpinfo` |
| 单元测试 | ✅ 有（含两端同一组哈希向量） |
| **界面入口** | ❌ **没有** |

验证方式：
- 全仓库搜「上传」，只有一个模块出现该词（`DeviceTasks.tsx` 的任务状态文案）；
- 公开 API `api.pickUploadSource()` **没有任何界面组件调用**；
- 下载中心只有三个标签：本机下载 / 设备任务 / 商店，没有上传；
- 文件管理工具栏只有：新建文件夹 / 下载到本机 / 兼容下载。

也就是说：**一条完整实现的上传链路，用户点不到。**

## 为什么会有这个结果（不是 bug，是范围）

本目标的原文里，文件管理那一项写的是"补格式图标与文件预览、修新建文件夹重复"，
下载中心写的是"支持添加链接/剪切板监听/BT 磁力" —— **都没有要求上传**。
所以这不是实现出错，而是**一个做完了但没接进界面的能力**。

## 为什么值得记下来

1. **"没验证过"的另一种形态**：前几轮是"实现了但只在客户端坏"，这次是"实现了但根本进不去"。
   两者都不会被单元测试发现 —— 因为测试直接调用 SDK，绕过界面。
2. **能力矩阵需要如实反映**：上传不能算"功能可用"，也不能算"没有"。
3. 真要做，工作量不大：文件管理工具栏加一个「上传」按钮 →
   选文件（原生用 `nas_upload_pick` 对话框 / 网页用 `<input type=file multiple>`）→
   调 `api.upload(...)`，进度进任务中心第四个标签。**但它需要真机验证**（我登不上），
   而现在没有任何证据表明上传在真机上能跑通 —— 直接接一个没验证过的入口，
   风险比"暂时不接"更高。

## 结论与建议

- **保持现状**（不接入口），并在能力矩阵里标成 ⏳"已实现/无入口/未验证"；
- 如果你要这个功能，告诉我一声 —— 我按上面三步接进去，**但需要你在能登录时配合验一次上传**；
- 如果你确定不需要，也可以把这条链路删掉（约 1500 行 + 原生三个命令），
  让代码库与实际能力一致。

## 顺带核对过、**没有**问题的部分

- 原生保存对话框的**取消**路径：有用例覆盖（取消或旧回调都不产生文件）；
- 选定路径在回调边界上**立即固化**（避免 TOCTOU）；
- 下载事件的进度名两端一致（见 `2026-10-12-native-media-cookies.md` 同批核对）。
