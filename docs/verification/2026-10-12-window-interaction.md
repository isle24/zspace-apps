# 窗口管理交互：查到一个真问题，以及一次"假的失败"

桌面壳的窗口交互（拖动、缩放、双击最大化、层叠聚焦、⌘W、越界夹取）是核心手感，
但前三十轮只验过"能打开 / 能关闭"。这轮补测，结果有一半是**测量方式的问题**。

## 真问题：资源挂件的外框挡住了窗口标题栏

实测几何：

| 元素 | 位置与尺寸 |
| --- | --- |
| 资源挂件外框 `.resource-widget` | x 1189–1549，**y 14–58**，360×44 |
| 窗口标题栏 | y 24–68 |
| 窗口默认位置 | y = 24 |

**外框比可见内容大**：胶囊是圆角（22px）的，但外框是方的、而且 `pointer-events: auto`。
于是胶囊圆角之外那四个方角区域变成"看不见的死区"——点下去不会落到下面的标题栏上：

```
修复前：elementFromPoint(外框左上角) -> .resource-widget   ← 点了个寂寞
修复后：elementFromPoint(外框左上角) -> .system-bar        ← 正常穿透到下层
```

修法：外框 `pointer-events: none`，只让**可见可点的部分**（胶囊按钮、展开的卡片）接收事件：

```css
.resource-widget { pointer-events: none; }
.resource-widget > * { pointer-events: auto; }
```

挂件是点击展开（不是 hover 展开），所以去掉外框的指针事件不影响它工作。

## 假的失败：后台窗口里 CDP 输入根本不会送达

第一次跑交互测试，结果是：

```
拖动: 位移 0 0 ✗      缩放: 766x440 -> 766x440 ✗
最大化: max=false ✗   ⌘W: 2 -> 2 ✗
```

看着像窗口管理全线崩了。查下去发现：

- `document.hidden === true` —— 这个 Chrome 窗口在**后台**（用户不在电脑前，窗口被遮挡/最小化）；
- 在页面不可见时，Chrome **直接丢弃** `Input.dispatchMouseEvent` / `dispatchKeyEvent`；
- 证据：连挂在 `document` 上的**捕获阶段**监听器都收不到 `pointerdown`，
  而 `elementFromPoint` 明明指向 `window-titlebar`；
- 同一个脚本在页面可见时，点窗口切换焦点是**正常**的（第一轮实测通过）。

也就是说那四个 ✗ **什么都没测到**。真实的结论只能是"未验证"。

所以 `scripts/window-interaction.mjs` 开头加了前置检查：

```
SKIP：页面处于后台（document.hidden=true），CDP 输入不会送达，测了也没有意义。
      请把浏览器窗口切到前台后重跑。   （退出码 2）
```

`verify.sh --live` 把退出码 2 记为 **SKIP**，不计失败，也不计通过。

## 换个办法继续：页内合成事件（处理器级）

页面不可见时 CDP 输入送不到，但**页内合成 `PointerEvent` / `KeyboardEvent` 可以** ——
它验证的是**应用自己的事件处理逻辑**（拖动状态机、缩放、双击最大化、快捷键、夹取）。
脚本据此分成两种模式，并在输出里写明结论属于哪一档：

| 模式 | 触发条件 | 结论强度 |
| --- | --- | --- |
| real | 页面可见 | 真机级（含指针捕获与系统输入路径） |
| synthetic | 页面在后台 | **处理器级**（不含指针捕获与系统输入路径） |

最终结果（synthetic，视口 1612×829）：

| 项 | 结果 |
| --- | --- |
| 拖动 | ✓ (355,29) → (455,49)，位移与指针一致 |
| 缩放 | ✓ 1100×640 → 1200×697 |
| 双击最大化 / 还原 | ✓ 1546×697 ↔ 1200×697 |
| 层叠聚焦 | ✓ 点击后 z 由 6 升到 8 并取得 `focused` |
| ⌘W 关闭 | ✓ 窗口数 2 → 1 |
| 越界夹取 | ✓ 落点 (66,0)，在应用自己的可用区域内 |

## 顺带补的功能：⌘W / ⌘M

测的时候才发现——**⌘W 压根没实现**（全局快捷键只有 ⌘K 搜索）。对桌面客户端来说
「关最前窗口 / 最小化最前窗口」是基本习惯，于是补上：

```ts
if ((e.metaKey || e.ctrlKey) && (e.key === "w" || e.key === "m")) { … }
```

- 目标是**当前作用域里 z 最大且未最小化**的窗口；
- **全部最小化后按 ⌘W 不误伤任何窗口**（没有"最前窗口"就什么也不做）；
- 注意：浏览器里 ⌘W 归浏览器管（`preventDefault` 拦不住），网页版会关标签页；
  到原生客户端才真正生效。⌘M 两边都能用。

两条用例覆盖：⌘W 关闭、⌘M 逐个最小化且全部最小化后不再误伤。

## 我的巡检脚本自己出了四个 bug

这轮值得记的不是功能，而是**测具**：

1. **`map` 变量作用域写错**：我把事件名映射留在了 Node 侧，页面里 `map["pointerdown"]`
   直接抛 `ReferenceError` → 一个事件都没派发 → 所有交互项报"没反应"。
   而 `ev()` **把页面异常吞成了 undefined**，于是这个错误静静躺了两轮。
   → 现在 `ev()` 遇到页面异常直接抛，不再静默。
2. **合成事件是同步的、React 重渲染是异步的**：派发完立刻读 DOM，读到的是旧布局
   → 误判"没动"。→ 每步后等一拍。
3. **拖动方向踩到夹取边界**：应用把可用区域算成 `innerHeight - 132`，
   按 (+120,+72) 向下拖时 y 只走了 28 就被夹住 → 看着像 bug，其实是对的。
   → 改成小幅右下，并按应用自己的公式断言范围。
4. **测试之间互相污染**：布局巡检的 `setDeviceMetricsOverride` 会残留，
   后续交互就在 880×620 的假视口里跑（夹取边界全变）。
   → 交互脚本自己带 `--reset`：刷新页面拿回真实视口（实测**只有刷新能清掉**别的会话设的覆盖）。

四个都是同一类：**测试说"功能坏了"，其实是测试自己坏了**。

## 这是第四次"尺子坏了"

1. 对比度合成把 alpha 置 1 → 凭空报 98 个问题
2. 窗口类名写错（`.window` vs `.app-window`）→ 量了整个桌面
3. 后台标签页 + `loading="lazy"` → 图片永远量到 0
4. **后台窗口 + CDP 输入不送达 → 交互项全部"失败"**

第 4 条与第 3 条同源（页面不可见），所以处理方式也一样：**让脚本自己发现并拒绝给结论**，
而不是输出一个看起来像功能坏了的 ✗。
